# Test strategy

How the project is tested, from cheapest to most thorough. Everything in sections 1–5 runs in `cargo test`, `pnpm test`
and `.github/workflows/ci.yml`, without ROMs. `tools/ci.sh` runs all of CI locally before every merge, plus
`cargo deny check` (`deny.toml`) and, with `PPR_TEST_ROMS` set, the tests on real ROMs.

## 1. Unit tests

Every crate tests its own parts. Randomizers run on in-memory games (`ppr-random`'s `testing` module), and formats on hand-built bytes. The frontend's option engine, `toSettings` / `fromSettings` and
helpers are covered by Vitest, and `src/lib/app.test.ts` drives the app's state the way the UI does (open, randomize,
cancel, settings strings and files, premade seeds, batches) against the mock backend.

## 2. Property and randomized tests

- `proptest`: seed display and parsing, EXP curves, starter and wild randomizer invariants.
- `fromSettings` gives back the settings it came from for 300 random option sets, drawn from every option of
  every group.

## 3. Synthetic fixtures

`ppr-romio::testing` builds a synthetic Emerald from its ROM entry and a few tables, so handler, service and CLI
tests can load, randomize, write and reload a game. No copyrighted data is involved.

## 4. Differential tests against a reference implementation

A reference harness, kept outside this repository, runs the reference implementation and writes its output:

- **Without ROMs**, committed as fixtures: 200 settings strings that the reference wrote, which must decode and
  re-encode byte for byte, and a `.rndp` premade seed file that the reference wrote.
- **With ROMs**: what the reference reads from each game (species, moves, learnsets, trainers, encounters, items, the type
  chart, palettes, …) and what some of its randomizers and tweaks do. The tests pin the output as hashes, or as
  values for small things, and compare our code with them. For Game Boy games they compare with a whole `GbDump`
  file instead, and for Gen 4, Black 2 and X with a whole `Dump` file; `PPR_REFERENCE_DUMPS` points to them. The data
  itself is never committed.

## 5. Contract tests

The TypeScript types in `src/lib/generated` are generated by `ts-rs` during `cargo test`. CI fails when they differ
from the committed ones. `svelte-check` then type-checks the frontend against them.

## 6. Local ROM tests

`#[ignore]` tests that run when `PPR_TEST_ROMS` points to a folder of your own dumps (Yellow, Crystal, Ruby 1.1, Emerald,
FireRed 1.0, Platinum (Europe) and Black 2 so far):

```sh
PPR_TEST_ROMS=~/roms cargo test --workspace -- --include-ignored
PPR_TEST_ROMS=~/roms PPR_REFERENCE_DUMPS=~/reference-dumps cargo test -p ppr-romio gen1 -- --include-ignored  # with the GbDump reference files
```

They load, randomize, save and reload every game, and check the invariants and the references of section 4.
Run them before merging anything that touches a ROM handler or a randomizer.

## 7. Fuzzing

`fuzz/` holds `cargo-fuzz` targets for what reads untrusted bytes. It is its own workspace, as it needs nightly
Rust and libFuzzer (`cargo install cargo-fuzz`, `rustup toolchain install nightly`).

| Target | Reads | Also checks |
| --- | --- | --- |
| `lz10` | LZ10 data | compressing round-trips |
| `blz` | BLZ data (DS overlays and ARM9) | compressing round-trips |
| `narc` | NARC archives | what reads rebuilds readably |
| `nds_rom` | DS ROMs: file system, overlays, ARM9 | a ROM with a replaced file saves |
| `settings` | settings strings and `.rnqs` files | what reads writes back readably |
| `premade_seed` | `.rndp` files | what reads writes back readably |
| `gen3_rom` | a synthetic Emerald with fuzzed bytes over its tables | a loaded game applies and saves |

```sh
cargo +nightly fuzz run settings -- -max_total_time=300
```

A crash lands in `fuzz/artifacts/<target>/`; `cargo +nightly fuzz run <target> <file>` replays it. Fix it and add a
unit test for the input, so stable `cargo test` keeps it fixed. Corpora and artifacts are not committed.

## 8. Coverage

```sh
cargo llvm-cov --workspace --exclude ppr-desktop --html   # Rust; target/llvm-cov/html/index.html
PPR_TEST_ROMS=~/roms cargo llvm-cov --workspace --exclude ppr-desktop -- --include-ignored  # with the ROM tests
pnpm coverage                                             # frontend; coverage/index.html
```

`cargo-llvm-cov` needs `cargo install cargo-llvm-cov` and `rustup component add llvm-tools`. There is no
threshold: coverage shows what the tests miss, it isn't a goal. At the time of writing the Rust crates reach about
92% of lines with the ROM tests.

## 9. End-to-end

`e2e/smoke.mjs` drives the built desktop app through `tauri-driver` (WebDriver): it opens a ROM, picks random
starters, randomizes, and checks the saved ROM and its log. It has no dependencies beyond Node. File dialogs take the
answers the test puts in `window.__PPR_DIALOG_ANSWERS__` (`src/lib/tauriBackend.ts`). The app gets a profile of its
own, and on Linux runs on Xvfb when that is installed, so no window appears.

```sh
cargo install tauri-driver
pnpm tauri build --debug --no-bundle
PPR_E2E_ROM=~/roms/emerald.gba pnpm e2e
```

It needs the platform's WebDriver: WebKitWebDriver on Linux (Fedora `webkitgtk6.0`, Debian and Ubuntu
`webkit2gtk-driver`) or msedgedriver on Windows. macOS has none for WKWebView. Without `PPR_E2E_ROM` it skips.

## 10. README screenshots

`e2e/screenshots.mjs` drives the built app the same way and writes the README's screenshots to
`docs/screenshots/`: the start screen, the randomizer with Emerald open on the Starters tab, the Manual edits
Trainers section, the starter picker, the dialog after randomizing and saving, and the batch randomization dialog. The
window is 1280×800 in the dark theme, clicks go through the page so nothing shows a hover state, transitions are off,
and the game is randomized with a fixed seed, so a rerun gives the same pictures. Until the app has the Manual edits
tab, the script skips that shot and says so.

```sh
pnpm tauri build --debug --no-bundle
PPR_SHOT_ROM=~/roms/emerald.gba pnpm screenshots
```

It needs Linux with Xvfb, `tauri-driver` and WebKitWebDriver. The profile and the saved game go to a throwaway folder
in `~/.cache/ppr-tmp` (`PPR_SHOT_TMP`), which is deleted afterwards; `PPR_SHOT_OUT`, `PPR_SHOT_SEED` and
`PPR_SHOT_APP` change where the PNGs go, the seed and the app. The script's header lists the details. Retake the
screenshots when the UI changes visibly, and look at every PNG before committing them.
